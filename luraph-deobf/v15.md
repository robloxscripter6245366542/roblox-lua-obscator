# Luraph v15 — what changed, and what it means for deobfuscation

Luraph v15 (announced 11 Aug 2026) is a **ground-up rewrite**, not a point
release. This note maps the announced changes onto the deobfuscation surface
and marks, honestly, which parts of this toolkit still apply and which need a
real v15 sample to finalise.

> **Status:** the feature-level notes come from the v15 announcement; the
> **byte-level model below is now measured against a real `Luraph Obfuscator
> v15.0` sample** (`sample_v15.lua` in this folder). Confirmed facts are
> marked **[measured]**; anything still open is **[needs sample]**. Nothing
> here fabricates magic bytes.

---

## Measured v15 format (from `sample_v15.lua`)  [measured]

A real v15.0 build is structurally different from the v14.7 bootstrap:

- **No `loadstring` bootstrap, no LZMA.** The whole program is a single
  `return setmetatable({ ... }, ...)` expression. The v14.7 chain
  (base-85 → **LZMA1** → VM source + separate bytecode stream) is gone.
- **One `[=[LPH…]=]` packed stream** holds the VM buffer. Decode is:
  1. `string.gsub` the stream through a **per-build character-substitution
     table** — a randomised table literal mapping single chars to (usually
     5-char) expansions, e.g. `IA={[" "]="Wgv\9",["("]=";5{w;", …}`. This
     generalises v14.7's single `z`→`!!!!!` zero-run shorthand. `peel.py`
     now auto-extracts this map (`extract_v15_submap`) by shape.
  2. **base-85** (same Ascii85 variant as v14.x) → `buffer.fromstring`.
  There is **no compression layer** — the bytes are already near-max entropy
  because they are **encrypted**, not compressed.
- **The VM buffer is XOR-stream-encrypted at rest and decrypted lazily
  during execution.** The read path is literally
  `buffer.writeu8(dst, i, bit32.bxor(k, buffer.readu8(buf, i), k2))` — every
  opcode/operand byte is `bit32.bxor`'d with a rolling key as it is read
  (93 `bxor` sites over 246 `readu8` reads in the sample). So a **static**
  peel legitimately cannot produce readable bytecode: `peel.py` recovers the
  buffer as `stage_N.v15buf.bin` and labels it runtime-encrypted. This is the
  concrete realisation of the `LPH_PRECHECK`/key-binding direction.
- **Threaded / continuation-passing dispatch, not a switch loop.** Instead of
  v14.7's single ~53 KB `o` with a binary search on the opcode, v15 has
  **~140 small named handler functions** (`s`, `Fu`, `tA`, `X`, …). Each
  takes the VM register tuple, does a short `if m<=N … elseif …` decode, and
  **returns `next_handler_id, regs…`**; a driver loop threads from handler to
  handler. This is the "unrolled VM" the announcement describes.
- **Library calls are cached in numeric table slots.** The same table holds
  `[94]=buffer.readu8`, `[37]=buffer.writeu8`, `[68]=bit32.bxor`,
  `[47]=bit32.rshift`, `[16]=bit32.band`, `[66]=bit32.lshift`,
  `[64]=buffer.readu32`, `[70]=buffer.readstring`, `[39]=buffer.readf64`,
  `[42]=buffer.fromstring`, `[81]=string.gsub`, … (83 numeric slots). Operand
  decoding is byte-wise varint (`%128`, `*128`, `*16384`, `*2097152` = 2^7 /
  2^14 / 2^21 shifts), read straight from the Luau `buffer`.

What this means in practice: `peel.py` + `fingerprint()` fully characterise
the **container** (substitution map + base-85) and prove there is **no static
codec** past it; recovering the actual instructions requires running the VM
and capturing the decrypted buffer / dispatch trace (the `dynamic/` path).

## The headline correction

The v14.7 writeup's central finding was: *the outer protection uses no
cryptographic key, so the whole thing unpacks statically.* **v15 can break
that** via a new macro:

- **`LPH_PRECHECK(fn, expected_return)`** inlines a user integrity function
  into the loader and **uses its return value(s) as a key to encrypt the main
  script's bytecode**. Decryption only succeeds if `fn` returns the expected
  integers at runtime. Example from the docs binds `game.PlaceId` and the
  local `UserId` into the key.

Consequences for us:

- W1/W1b ("outer packing is reversible encoding, not encryption") and W5
  ("anti-tamper is a patchable value-poison, not a wall") are **no longer
  unconditionally true**. On a script that uses `LPH_PRECHECK`, a static
  `peel.py` will legitimately *fail* to reach the bytecode — that's the design
  working, not a bug. Recovery then requires running the loader in an
  environment that supplies the right platform values (see `dynamic/`), i.e.
  the key must be *observed*, not derived offline.
- Even without `LPH_PRECHECK`, the rewrite means the container and codec are
  **[needs sample]** — do not assume base-85 → `LZMA1(lc3,lp0,pb0)` / `D=5`.
  `peel.py` now auto-detects the header length and reports honestly when the
  inner stream does not LZMA-decode instead of emitting garbage.

## Two VMs: OPAL and ONYX

v15 ships **two ISAs**, selectable per function via the new attribute system:

- **OPAL** — default VM, balances performance and security.
- **ONYX** — new VM, prioritises security over performance.

Impact: the opcode map is now **per-VM-type as well as per-build**. The
`devirt/` register-delta approach still applies in principle, but a build can
mix OPAL and ONYX functions, so the census/map stage must be run and kept
**separately per ISA**, and the fingerprint must tell them apart. **[needs
sample]** to characterise each ISA's dispatch shape and operand encoding.

## New attribute / macro system (the analysis surface)

Comment-style macros are replaced by `LPH_ATTRIBUTES(...)` as the **first
statement** of a function body — chosen specifically so expressions integrate
with real parsers/formatters. Relevant attributes and macros:

| v15 construct | Replaces / new | Why a deobfuscator cares |
|---|---|---|
| `VM(OPAL\|ONYX\|NONE)` | `LPH_NO_VIRTUALIZE` (=`VM(NONE)`) | picks the ISA (or none) per function |
| `PRESET(FAST\|SECURE\|…)` | `LPH_JIT` (=`PRESET(FAST)`) | obfuscation intensity |
| `TRANSFORM(CONTROL_FLOW, EXTRACT)` | new | AST obfuscation on **non-virtualized** code — flattening/extraction you now meet outside the VM |
| `INLINE` | new | fully-optimised inlining (upvalues + variadics); callee body vanishes into caller |
| `UNROLL` | new | numeric-for unrolling with computable bounds |
| `LPH_REWRITE(expr, {preset,budget,context})` | new | **Mixed Boolean Arithmetic** rewriting of arithmetic/bitwise expressions — constant folding/MBA-simplification is now part of lifting |
| `LPH_ENCSTR/ENCNUM/ENCBUF(..., key?)` | extended | encryption macros now take a user key (string / int / `{bytes}`); `ENCBUF` is new for Luau `buffer` |
| `LPH_STACKALLOC(size, zeroOrOne?)` | new | arrays placed directly on the VM's virtual registers instead of a table — a `t[k]` you can't find as a table alloc |

Note these are **compile-time directives in the input** — they are consumed
during obfuscation and generally do **not** appear verbatim in the output. So
scanning obfuscated output for them is only a weak tell (it catches leftover
artifacts / un-obfuscated wrappers). Their real relevance is that they tell
you *what transformations the output has already been through* — MBA in
arithmetic, inlined/unrolled bodies, non-virtualized-but-flattened functions.

## Other v15 notes

- **Non-virtualized code is now strongly bound to virtualized code** — a
  child function can switch back to a VM via `VM(...)`. Expect mixed
  virtualized/native within one call tree.
- **goto-rewriting**: v15 auto-rewrites unsupported syntax (e.g. Luau `goto`)
  in non-virtualized code — another source of synthetic control flow to undo
  when reading `TRANSFORM`'d functions.
- **Performance/loadtime** improvements are noted; not directly relevant to RE
  beyond possibly smaller/faster loaders.

## What this toolkit already does correctly for v15

- **Fingerprint** (`deobfuscate.py` stage 0 / `fingerprint()`): detects the
  `v15` version string, infers v15 from `LPH_*` / `VM()` markers, reports
  OPAL/ONYX when visible, and prints the v15 caveats instead of silently
  applying v14.7 assumptions.
- **`peel.py`**: auto-detects the header length instead of hardcoding `D=5`,
  and when the inner stream does not LZMA-decode it says so and points at the
  runtime path (`LPH_PRECHECK` key-binding / new codec) rather than writing a
  bogus "decrypted" stage.
- **Regression-safe**: the v14.7 sample still peels byte-for-byte identically.

## Status of each item

1. **Container + codec** — **[measured]** substitution map + base-85, **no
   LZMA**; `peel.py` handles it and emits the runtime-encrypted buffer.
2. **Runtime XOR decryption** — **[measured]** `bit32.bxor` in the `readu8`
   path; static recovery of instructions is not possible past the buffer.
3. **Dispatch model** — **[measured]** ~140 threaded continuation handlers
   with cached numeric library slots (not a switch/binary-search loop).
4. **OPAL vs ONYX ISAs** — **[needs sample]** the current sample doesn't name
   its ISA in output; still need builds that isolate each VM to characterise
   opcode field widths and per-ISA maps for `devirt/`.
5. **`LPH_PRECHECK` platform key** — **[needs sample]** capture the concrete
   values mixed into the key and wire a runtime-assisted decode into
   `dynamic/` (booting the threaded VM under a stubbed env).
6. **MBA (`LPH_REWRITE`)** — **[needs sample]** an MBA-simplification pass for
   the lifter so rewritten arithmetic folds back to readable expressions.
7. **`LPH_STACKALLOC`** — **[needs sample]** recognise register-array patterns
   so stack-allocated arrays lift back to indexed access.

`sample_v15.lua` (committed here) is the fixture for items 1–3. Items 4–7
need additional builds that exercise those specific features.

## Dynamic tracing — `dynamic/run_v15.py`  [measured]

The v15 analogue of `devirt/run_vm.py` now exists and is verified on
`sample_v15.lua`. Because v15 has no separate VM-source to boot, it wraps
`setmetatable` and replaces every handler field of the VM table with a tracer
*before* the driver fetches it (std-lib primitives are identity-checked and
left real so the decrypt loop stays fast). It produces:

- **`.hist.txt`** — per-handler call histogram. On the sample a 5-handler
  cycle (`Mu Nu Lu ou hu`, ~33 K calls each) dominates and the bootstrap `XA`
  fires exactly once.
- **`.seq.txt`** — the handler-transition trace (`handler -> next_id`), i.e.
  the **executed opcode stream**: a tight repeat `ou->23 Lu->37 Nu->13 Mu->8
  hu->29 …` = the per-instruction decode/dispatch loop.
- **`.writebuf.bin`** — the most-written buffer, which turns out to be the
  VM's low-entropy scratch/register space (~0.46 bits/byte), **not** the
  bytecode.

This **dynamically confirms** the lazy per-read XOR model: there is no
monolithic decrypted buffer, so the instruction stream is only observable
from the dispatch trace, not by dumping memory.

## Opcode/handler map — `devirt/v15_opcodes.py`  [measured]

`devirt/v15_opcodes.py` builds the opcode map: it statically classifies every
handler (arity, the numeric library slots it calls — resolved to
`buffer.*`/`bit32.*`/`string.*` via the sample's own `[N]=lib` table, the set
of `next_handler_id` successors it returns, and a heuristic category) and
overlays the dynamic coverage from `run_v15.py`'s histogram. Committed output:
`devirt/v15_opcode_map.md` + `devirt/v15_opcodes.json`.

On `sample_v15.lua` (Luraph v15.0):

- **145 handlers defined**, 83 cached library slots.
- **Every handler is statically classified — 0 unknown.** The bulk are
  `FETCH|BRANCH` (52; operand fetch + multi-way dispatch) and
  `FETCH|STORE/DECRYPT|BITWISE|BRANCH` (35; the `bit32.bxor`+`writeu8` decrypt
  handlers), plus `TABLE/CONST` loads, `RESUME` (return a control flag + next
  id), `ARITH` (u32 wrap), `STORE-NIL`, etc. The `ou` handler is the
  substitution-map loader (`string.gsub` + `buffer.fromstring`).
- **68 handlers are exercised** by this sample; **77 are defined but never
  hit** — these are the *remaining opcodes*, listed in the map and in
  `never_exercised`. They need samples whose programs use those operations to
  observe their runtime successors/register effects.

## Payload recovery harness — `dynamic/deobf_v15.py`

To recover the *program's* own behaviour (remotes, URLs, target logic) rather
than the VM structure, `dynamic/deobf_v15.py` gives the VM a rich, fully
network-/disk-blocked Roblox + executor emulation (task/game/GetService/
Instance/datatypes/`identifyexecutor`/`debug`/http/fs — every sink stubbed and
logged) and runs the sample, capturing `[[URL]]`/`[[SERVICE]]`/`[[REMOTE]]`/
`[[INSTANCE]]`/`[[STR]]`/`[[FS]]` events.

**What it solves** [measured]: the minimal `run.py` env aborts the v15 VM at
`nil.cancel` — the loader indexes Roblox globals the bare Luau CLI lacks. The
rich env fixes exactly that: the VM boots past its executor/debug gate and
enters the payload's decrypt/dispatch loop.

**Current limitation** [measured, revised twice]: this is nested
interpretation — a virtualised VM running inside the Luau interpreter — and
on `sample_v15.lua` the payload's remotes/URLs had not surfaced within a
multi-minute budget. Earlier notes attributed this purely to raw
interpretation speed, then (after instrumenting a local Luau build's
`lua_callbacks(L)->interrupt` hook and sampling every 2M interrupts) to a
single dispatch loop (`T==103`) spinning over a ~400-instruction span
forever. Both undersold or mischaracterized it. `devirt/v15_payload_probe.py`
now gets ground truth by injecting a print probe directly after each
dispatch loop's opcode fetch and running the probed sample through this same
harness — a real per-opcode dynamic histogram, not inference from a handful
of sampled snapshots:

- The *payload's own bytecode interpreter* — a second, inner VM distinct
  from the 145-handler loader VM `devirt/v15_opcodes.py` maps — is written
  directly in `sample_v15.lua`'s source as **four** `while true do local
  M=ARR[w] ... end` dispatch loops sharing one pc variable (`w`), each a
  binary-search switch on its own opcode fetch (`M=o[w]`, `M=E[w]`, `M=r[w]`,
  `M=o[w]` again on this sample — Luraph reuses whichever of the six parallel
  arrays for each mode). A `M`-opcode in one mode can switch to a different
  mode (reassigning the mode-select register and jumping into a different
  loop) — this is how the payload's control flow crosses between the four
  instruction subsets. This is what the earlier interrupt-hook sampling
  actually observed staying in "one function" for 500M+ interrupts: all four
  loops are sibling blocks of the *same* enclosing closure, so the active
  Lua function pointer never changes even while execution legitimately moves
  between all four modes — that stability was never evidence of being stuck
  in `T==103` specifically, and the follow-up correction naming that mode was
  itself wrong.
- The probe's real numbers (`devirt/v15_payload_opcode_map.md`, regenerate
  with `python3 devirt/v15_payload_probe.py sample_v15.lua`): all four modes'
  pc range spans the *entire* program (~1–4260, not a narrow slice). Three of
  the four modes execute an exact, run-length-independent instruction count
  (760,225 / 492 / 1,654 across two independently-timed runs) — they do a
  fixed amount of work, presumably during the payload's own bootstrap, and
  are never revisited. The fourth mode (opcode fetched via `r[w]`) is the one
  that grows without bound as the run's time budget grows — over 15M
  instructions in a 30s run, 65 distinct opcodes hit, dominated by two
  opcodes with identical counts (`16` and `88`, ~2.1M each — plausibly a
  paired read/write) then `61`, `50`, `53`, `45`, `70`, `54`. That mode,
  cycling across the full instruction range with no sign of settling, is the
  genuine unbounded loop; the other three are not part of the problem at all.
- No `[[URL]]`/`[[REMOTE]]`/`[[STR]]`/`[[SERVICE]]`/`[[INSTANCE]]` events
  surfaced in any probe run — the interesting payload behaviour lives on the
  far side of this loop's exit, which this stub environment never triggers.

Net effect: "slow" undersold it, and "stuck in `T==103`" was too specific and
wrong about *which* mode and *how much* of the program it spans — under the
current stub environment this mode's loop may not terminate at all,
regardless of how fast the outer Luau interpretation runs (a faster/JIT Luau
would only make it spin faster, not exit).

**Opcode semantics** [measured] — `devirt/v15_payload_opcodes.py` closes the
first of the two ways forward below. Rather than the register-delta approach
`devirt/semantics.py` uses for v14.7 (diffing live register snapshots, which
sidesteps needing the source), this parses the exact `luau-ast` JSON of each
dispatch loop's if/elseif chain directly (regex can't safely walk arbitrary
nested Lua bodies the way it walks v14.7's flat `NAME=function()...end`
handler list) — resolving each leaf's exact opcode value/range from its
guard chain and classifying its body (library calls, register arrays
touched, jump/call/return/loop shape), then overlaying the dynamic counts
from `v15_payload_probe.py`. Committed output: `devirt/v15_payload_opcode_semantics.md`
+ `.json` (regenerate with `python3 devirt/v15_payload_opcodes.py sample_v15.lua
--luau-ast dynamic/luau-ast --hist devirt/v15_payload_opcodes.json`, which
needs `dynamic/build_luau.sh` to have also built `luau-ast`, the AST-dumper
CLI target it now builds alongside `luau`). Findings:

- **305 opcode branches classified** across all four modes (54/58/105/88),
  matching the manually-verified count for mode 0 from the earlier
  investigation exactly.
- In the hot, unbounded mode (`M=r[w]`, dominates with 15M+ instructions):
  several high-frequency opcodes (`16`, `88`, `61`, `90`, `91`, each hit
  hundreds of thousands to millions of times) are classified `JUMP`
  (reassign `w` directly) and others `CALL` (invoke a sibling helper
  closure — `53`→`m`, `54`→`j`, `29`→`Q`) — this is a real, branchy,
  call-heavy control-flow loop, not a degenerate spin. Its two `RETURN`-
  category opcodes (`33`, `41`) have a **dynamic count of 0** in every
  probe run so far: the loop's only classified exits are never reached
  under this stub, consistent with (and now more precise than) the earlier
  "no sign of settling" observation.
**Codegen** [measured] — `devirt/v15_payload_dump_arrays.py` captures the
VM's fully-decoded instruction data (the real `o`/`r`/`k`/`E`/`R`/`t`/`L`
array contents, not a narrow window) by injecting a one-shot dump probe
directly into the sample's source right after the target dispatch loop's
opcode fetch — since the probe is source-level, it has ordinary lexical
access to whatever upvalues are in scope there, no C-side instrumentation
needed. (One real bug surfaced and fixed while building it: `deobf_v15.py`'s
harness redacts any printed string over 120 chars to `<str N>`, and its
`%q`-quoted log line's closing quote was being swallowed into the last
value of each chunk — both fixed by chunking the dump to 8 values per print
and stripping the trailing quote.) `devirt/v15_payload_lift.py` then
combines that data with `v15_payload_opcodes.py`'s per-opcode AST templates
to do genuine per-instruction codegen: `R[r[w]]=R[k[w]]<E[w]` (the
*template*, symbolic in `w`) becomes `R[7]=R[12]<58` (the *concrete*
instruction) once the real `r`/`k`/`E` values at that `w` are known — the
same job v14.7's `lift.py` does from decoded bytecode, just against a VM
whose interpreter is already plain Lua (read via `luau-ast`) instead of
opaque numeric handler IDs needing a curated map.

**Critical finding — the instruction arrays are self-modifying** [measured].
A static array dump is only a snapshot: re-running with a longer time
budget and comparing what a given `pc` decodes as shows array contents
*changing* at positions already visited (e.g. `r[3982]` read as `61` in an
initial snapshot, `6` when actually executed later in the same run) —
several opcodes' own bodies confirm this isn't a bug, they explicitly write
into `r[w]`/`E[w]`/`o[w]` as part of normal execution (op 40's body computes
values and assigns `r[w]=...`, `E[w]=...` directly). This is why
`v15_payload_lift.py` lifts the **trace order** (the real `(pc, opcode)`
sequence a run visited, from `v15_payload_probe.py`'s raw output) rather
than a blind static walk of `pc=1..N` — a static walk would silently lift
whatever the *first-snapshot* opcode at each position was, which need not
be what actually ran there on a later visit. Verified on a 300,000-
instruction trace: 0 unresolved among the first 5,000 steps, 1 unresolved
in 300,000 — the lifter works, but every lift is now honestly scoped to
"what this specific trace executed," not "the program." This reframes the
open question from "why doesn't a static branch reach the exit" to "this
VM incrementally decodes/rewrites its own instruction stream as it runs,
and under this stub it may simply not have unfolded far enough yet" — closer
to genuinely slow (self-decoding takes real steps) than a dead branch, but
for a different, more precise reason than either earlier theory.

**RETURN-opcode tracing — root cause found** [measured, confirmed]. The
`R[36]`/`R[105]`-starvation theory floated in an earlier revision of this
section is **wrong, and now disproven**: `devirt/v15_payload_watch.py` (a
low-overhead injected probe that watches for specific opcodes firing or
registers being written, instead of logging every instruction — cheap
enough to run into the billions of instructions) shows both registers get
written within the first ~1,500 instructions once *all four* dispatch
modes run together, not zero. The earlier "300k-instruction, single-mode
trace" that saw no writes was misleading precisely because of the
self-modifying-array finding above: the four modes interleave (a mode
switches, runs, switches back), and a mode-2-only trace simply never
observed the writes another mode was making in between.

Running that same watch **on mode 2 alone, for 4 billion executed
instructions** (two independent runs — 3.5B in one, 4B interleaved with
the other three modes in a second) shows mode 2's own `M==33` branch never
fires, ever, at that depth — so more depth alone would not have found it
either. Reading opcode `33` and `41`'s exact AST (both, independently)
shows an identical shape: `if Z then for p in J,Z,nil do ... return ...
end end` — a **conditional return gated on a variable `Z`**, not an
unconditional one. Injecting a one-shot probe to print `Z`'s live value the
moment opcode `41` fires (confirmed firing at instruction 66 of mode 2's
own count) shows **`Z` is `nil`** — the gate is shut, so the `for`/`return`
inside never executes at all; the opcode "firing" was never going to
terminate anything, independent of how long the run goes.

`Z` is a top-level local of the same enclosing closure as `R`/`T`/`w`
(declared in the same initial multi-variable `local` at the very start of
the function), assigned at exactly 3 sites across the whole VM (one each
in modes 1, 2, and 3), always via the identical pattern `<save
K=Z>; Y=t[F[4]](t,nil,<arg>,F,nil,nil); H(Y,N); R[<reg>]=Y; <restore>,Z=
<arg>,K` — a save-call-restore wrapper around invoking `t[F[4]]`, a
function looked up from the same 127-entry table (`t`) that
`devirt/v15_opcode_map.md` already identifies as a constant/handler pool,
selected by index `F[4]`. That is, `Z` is a piece of call-context state
saved before and restored after calling into a handler selected from the
*outer* loader's own table — plausibly an in-flight signal/continuation
value threaded through calls back into the 145-handler stage, though its
exact semantics (what would make it non-nil, and under what real condition)
have not been resolved; that is genuinely new ground, not something either
more depth or more static reading of *this* VM alone settles; it needs
either that outer call's real behavior, or a real executor providing
whatever ultimately feeds `t[F[4]]`'s result.

**Second, unexplored register-VM** [confirmed structure, not lifted]. The
same generic detector (`v15_payload_probe.py`'s `find_vm_groups`) finds a
*second* candidate VM earlier in the source (pc-var `Q`, opcode-var `J`,
operand arrays `n`/`P`/`f`), in the loader stage rather than the payload —
4 dispatch modes, 78/61/64/72 opcode branches (275 total), same shape as
the payload VM (JUMP/CALL/RETURN/LOOP-classified branches over parallel
arrays `D`/`H`/`W`/`c`/`T`/`m`/`n`/`P`/`f`). `v15_payload_opcodes.py`'s
walk applies to it unchanged (it's genuinely generic, not payload-specific)
but this VM has not been run under the dynamic probe or lifted — it's
confirmed to exist and its opcode categories are classifiable, nothing more.
Given the byte offset (well before the payload VM, in the same region as
the 145-handler loader), a plausible guess is this is the substitution-map
or constant-pool decoder v15.md's general architecture section already
describes, but that is a guess, not a finding.

**Portability across samples** [status]. All of `v15_payload_probe.py`,
`v15_payload_opcodes.py`, `v15_payload_dump_arrays.py`, and
`v15_payload_lift.py` locate their target purely structurally (the
`while true do local <M>=<ARR>[<PC>];` shape, grouped by shared pc-variable,
richest-comparison-count wins) — no hardcoded variable names, T-values, or
opcode numbers anywhere in any of the four tools (checked by inspection: the
only sample-specific input any of them takes is the sample path itself and,
for the lifter, the mode index to target). They have only ever been run
against `sample_v15.lua`, so this is a design claim verified by code
inspection, not by testing against a second real-world v15 sample — none is
available in this repo. Re-running the whole pipeline against a different
v15 build should work unmodified; whether it actually does is untested.

**`LPH_PRECHECK` (key-bound bytecode)** [blocked, unchanged]. Still needs a
sample that actually uses it, which this repo doesn't have — nothing to
report beyond what v15.md already says elsewhere; this is not something
more analysis of `sample_v15.lua` can resolve.

   `devirt/v15_payload_watch.py`. The register-starvation theory is
   retired; billions more instructions of tracing depth would not have
   found this, because it was never a depth problem.
4. **Resolve `t[F[4]]`'s real behavior.** `Z` is saved/restored around a
   call into the outer loader's handler table (`t`, 127 entries, selected
   by `F[4]`) — what that call is *supposed* to compute (and under what
   condition it would leave `Z` non-nil) is the concrete remaining
   question, and it's a call into the already-mapped 145-handler stage
   (`devirt/v15_opcodes.py`), not an unmapped black box. Tractable next
   step: instrument that specific call site to log `F[4]`'s value and
   `t[F[4]]`'s identity/result each time it fires, the same
   inject-a-probe-at-an-exact-offset technique every tool in this section
   already uses.
5. **Capture on a real executor**, as already documented above — still the
   most direct way past the self-modification depth and the
   environment-dependent condition, since real client state and real
   execution speed are exactly what a static stub and nested Luau
   interpretation can't supply. Given finding #3, this is now narrower
   than "run it on a real device and see" — it specifically means
   observing what makes `Z` non-nil there.
6. **Lift the second (`Q`) register-VM** — same tooling, unapplied; would
   need its own dynamic probe run and array dump the way the payload VM got
   both.

## Remaining last mile

Two concrete, bounded tasks remain for a full lift:

1. **Cover the missing 77 opcodes** — run `run_v15.py` on more v15 samples
   (varied programs) and re-run `v15_opcodes.py`; each new sample fills in
   handlers this one never reached. The map merges by handler name.
2. **Assign exact semantics + codegen** — the categories say *what family*
   each handler is; turning that into a precise Lua operation per opcode (and
   emitting source) is the manual, build-specific step, now fed by the map and
   the `run_v15.py` transition trace instead of guesswork.

Items 4–7 above (OPAL vs ONYX, `LPH_PRECHECK` key capture, MBA, `STACKALLOC`)
still want extra samples that isolate those features.
